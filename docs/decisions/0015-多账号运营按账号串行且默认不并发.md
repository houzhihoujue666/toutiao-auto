# ADR-0015 多账号运营按账号串行且默认不并发

## Context and Problem Statement

v0.1.0 一个进程只服务一个账号（`process.env.ACCOUNT_NAME || 'toutiao-main'`，发布队列是进程级单例）。
CHG-0002 要支持多账号（`docs/changes/0002-多账号运营/01-需求.md`），随之而来的取舍是：

**多个账号能不能同时发布？**

- 同账号并行是明确禁止的（红线 9 / ADR-6），多账号后这条必须靠结构保证而不是靠「当前只有一个人用」；
- 跨账号并行在平台侧是「不同用户」，但本机同一出口 IP、同时开多个浏览器，容易被判定为群控 —— 触 ADR-5（风控优先于效率）；
- 另一方面，多账号的收益本身更多是「隔离」（额度按账号叠加、一个账号掉登录不影响别人），未必需要并行才成立。

## Decision Drivers

- ADR-5：风控优先于效率
- ADR-6 / 红线 9：同一账号严格串行（多账号后需结构化保证）
- ADR-10：可调项进 `app_config`，安全项锁死在代码
- 本机单人工具：默认行为必须与改造前等价，放开要显式操作

## Considered Options

- **A：多账号完全并行**（每账号一条队列，无跨账号闸门）
- **B：多账号串行（一个全局名额）**，把名额做成可调项，默认 1
- **C：固定并行 2**（或按账号数的一半）

## Decision Outcome

选 **B**：**每个账号一条独立发布队列 + 队列锁保证同账号串行；跨账号另设「同时在发布的账号数」闸门（`accountConcurrencyLimit`），默认 1。**

理由：

1. 「隔离」是多账号的主要收益，「并行」不是 —— 默认 1 时多账号仍然带来额度叠加与故障隔离；
2. 默认 1 让本次改造的**默认行为与改造前完全一致**，老用户升级零感知；
3. 想提速的人需要显式调大该项（上限 5）并自行承担风险，责任边界清晰，符合 ADR-10。

### Consequences

- Good：红线 9 由「每账号独立队列 + 账号锁」结构化保证，不再依赖调用方自律。
- Good：默认行为等价 → 老库的账号（`toutiao-main`）零迁移接管。
- Good：并发策略是可调项而非硬编码，后续有实测数据要放宽时不必改结构。
- Bad：默认吞吐不提升 —— 这是有意取舍，写进设置项说明（"调大会提高风控风险"）。
- Bad：多一层调度器（等待队列 + FIFO 唤醒），复杂度上升；用单元测试锁住行为。

### Confirmation

- `backend/src/orchestrator/publishScheduler.ts`：上限默认取 `DEFAULT_ACCOUNT_CONCURRENCY`（=1），拒绝同账号重入以外的超额占用。
- `backend/src/orchestrator/queue.ts`：不再导出进程级单例；`Pipeline` 每实例持有自己的队列。
- 集成测试 `backend/tests/integration/multiAccount.test.ts`：并发上限为 1 时两个账号不会同时处于 `publishing`。
- 设置项 `accountConcurrencyLimit` 出现在 `/api/settings` 的可调列表且默认为 "1"。

## Pros and Cons of the Options

### A：多账号完全并行

- Good, because 吞吐最高，实现最省事（不要调度器）。
- Bad, because 同一 IP 同时开多个浏览器发布，直接违背 ADR-5；一旦被判定群控不可逆。

### B：每账号队列 + 全局并发闸门（默认 1）

- Good, because 同账号串行结构化保证；跨账号风险由可调闸门收口；默认等价旧行为。
- Bad, because 默认不提速；多一个调度模块。

### C：固定并行 2

- Good, because 折中，有一定提速。
- Bad, because 「2」是拍脑袋的魔法数，没有实测依据；且把默认行为从「串行」改成「并行」，风险偏好被悄悄抬高。
