# ADR-0014 文档治理采用三层模型与 ADR 取代机制

## Context and Problem Statement

项目要在「需求 → 设计 → 开发 → 验证 → 发布」的正规流程上持续加功能，现有做法是一份越写越大的设计文档
（`方案设计文档_20260910 → 精简版_20260920 → v4.0_20261012`，另加附录 E 补充记录）原地演进。带来的问题：

1. **旧结论被覆盖**：改了什么、为什么改，只在 git diff 里能看到，文档本身没有"版本"概念。
2. **阶段不可见**：看不出某个功能是哪个阶段定的、定案时依据是什么。
3. **事实与历史混在一起**：架构现状（常青）和某次设计方案（时点）写在同一份文件里，改哪边都不对。

需要一套机制，让"哪些变了、哪些沉淀、哪些归档"有明确答案，同时**不丢失已有文档**。

## Decision Drivers

- 加新功能时旧文档不能动（可追溯性优先于整洁）
- 目录要能一眼看出阶段与状态
- 单人 + 智能体协作，流程必须轻，能长期坚持
- 不引入额外系统（不上 Confluence / DMS），全部用仓库里的 Markdown

## Considered Options

- **A：单一大文档继续原地演进**（v4.0 → v4.1 → v5.0）
- **B：三层文档模型**（常青 / 决策 / 变更 + 归档），一次变更一个目录，冻结 + 取代 —— 参考 MADR、Spec Kit、KEP
- **C：迁到外部知识库**（Confluence / 网盘 / Notion）

## Decision Outcome

选 **B**，并把 A 的历史产物整体冻结进 `docs/archive/legacy/`（`git mv`，保留历史，原文不改）。

配套约定：

- 常青层（`10-architecture/` `20-reference/` `30-operations/` `00-guide/`）随代码改；
- 决策层（`decisions/`）用 ADR，冻结、只取代；新 ADR 从 0014 起编号；
- 变更层（`changes/NNNN-xxx/`）一次功能一个包，含 `01-需求` `02-设计` `03-任务` `04-验证` `05-发布`，批准即冻结；
- 版本基线：SemVer + git tag + 根 `CHANGELOG.md`（Keep a Changelog 六分类），提交用 Conventional Commits；
- 归档：`done` 满一个季度移入 `archive/YYYY-Qn/`，只在 `docs/INDEX.md` 留记录；
- 入口统一：`docs/INDEX.md`。

### Consequences

- Good：历史一字不丢，改动有编号可追；阶段与状态在目录上直接可见；智能体有稳定可读的意图来源（不再依赖聊天记录）。
- Good：规则轻（5 个模板 + 1 张总表），单人也能坚持。
- Bad：多了一层目录跳转，写小功能时要建包——用"迷你流程"（一个 `README.md` 走完）抵消。
- Bad：常青层与 legacy 会有短暂的内容重叠，需要按 `archive/legacy/FROZEN.md` 的沉淀清单逐步迁移，迁移期以常青层为真源。

## Confirmation

- 新功能是否建了 `changes/NNNN-xxx/` 包（或走了迷你流程）？
- `docs/INDEX.md` 变更总表是否更新？
- 发布是否更新了 `CHANGELOG.md` 并打 tag？
- 旧文档是否被修改过？（应当为零）
