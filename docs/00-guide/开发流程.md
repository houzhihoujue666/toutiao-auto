# 开发流程与门禁（常青层）

> 需求 → 设计 → 开发 → 验证 → 发布 → 沉淀。每一步有入口条件（DoR）和出口物（DoD）。
> 智能体（AI）按本文件执行；人按本文件验收。

版本：v1.0 · 生效：2026-10-23

## 一、阶段门禁

| 阶段 | 入口 DoR                      | 出口物（写入变更包）                | 出口 DoD（不满足不得进入下一阶段）                                        |
| ---- | ----------------------------- | ----------------------------------- | ------------------------------------------------------------------------- |
| 需求 | 一句话诉求 + 可判定的验收标准 | `01-需求.md`                        | 每条需求有唯一 ID 与可测试标准；写明 **Non-Goals**（明确不做什么）        |
| 设计 | 需求已 `approved`             | `02-设计.md`                        | 有 Context/Goals、≥2 个备选方案对比、列出横切关注点影响（安全/合规/限速） |
| 开发 | 设计已 `approved`             | `03-任务.md`                        | 任务按用户故事组织、带依赖、可勾选、能映射到需求 ID                       |
| 验证 | 开发完成                      | `04-验证.md`                        | 每条验收标准有测试证据；`npm run typecheck` / `npm test` 通过             |
| 发布 | 验证通过                      | `05-发布.md` + `CHANGELOG.md` + tag | 版本号符合 SemVer；回滚方案就位；`git push`                               |
| 沉淀 | 上线后                        | 常青层文档 + 必要 ADR               | 常青文档与代码一致；争议决策已入 `decisions/`                             |

## 二、开工前必读（AI 与人同样适用）

1. `docs/10-architecture/红线与约束.md` —— 10 条硬红线，违反即为不合格产出。
2. `docs/decisions/README.md` —— 已有决策，不要重复讨论已定案的事。
3. 本次变更包里的 `01-需求.md` / `02-设计.md` —— 意图的唯一来源，**不要从聊天记录里回忆需求**。

## 三、逐阶段 checklist

### 需求

- [ ] 每条需求写成可判定句：`WHEN … THEN …`（EARS 句式）
- [ ] 标注唯一 ID（`REQ-0007-01`）
- [ ] 写明 Non-Goals（本可以做但明确放弃的东西）
- [ ] 说明影响面：涉及哪些模块 / 表 / 接口

### 设计

- [ ] Context and Scope（客观背景，不写需求）
- [ ] Goals / Non-Goals
- [ ] 方案主体（先概览后细节），重点是**权衡**
- [ ] Alternatives Considered（≥2，说明为什么没选）
- [ ] 横切关注点：风控与限速、幂等与不可逆、合规（作品声明 / 首发）、数据脱敏
- [ ] 影响的文件清单

### 开发

- [ ] 契约（`shared/`）先行，前后端围绕契约开发
- [ ] 垂直切片：每步都是能真跑的链路，不铺空壳
- [ ] 提交信息符合 Conventional Commits，正文写变更包编号

### 验证

- [ ] 新增/更新测试，覆盖每条验收标准
- [ ] `npm run typecheck`、`npm test` 全绿
- [ ] 涉及界面：录一条前端测试或手工核对截图

### 发布

- [ ] 更新根 `CHANGELOG.md`（六分类）
- [ ] 打 tag（`vMAJOR.MINOR.PATCH`）
- [ ] 写回滚方案
- [ ] `05-发布.md` 记录实际结果与偏差

### 沉淀

- [ ] 架构/接口/配置变化 → 更新常青层
- [ ] 有争议或难逆转的决策 → 写 ADR
- [ ] 踩坑 → `postmortem/`
- [ ] 更新 `docs/INDEX.md` 变更总表

## 四、小改动的迷你流程

对齐 Google 的 mini design doc（1–3 页）：**阶段顺序不变，篇幅压缩**。

- ≤ 半天、方案无争议：一个变更包 `README.md`（含需求 + 设计 + 任务 + 验证）+ CHANGELOG 即可。
- 只要满足下面任一条，**必须走完整流程**：改数据结构/迁移、涉及发布不可逆动作、有 ≥2 种可选方案、动到红线相关代码、跨前后端契约。

## 五、什么时候不用写设计文档

- 方案不模糊、没有权衡（"就是这么实现"）→ 直接写代码 + 测试，CHANGELOG 记一笔。
- 只是修 typo、调样式、加日志。
- 判断标准：**是否存在"选错了会返工"的抉择**。没有就别写。
