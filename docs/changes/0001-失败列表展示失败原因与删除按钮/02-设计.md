# 设计：失败原因展示与失败任务删除

## Context and Scope

错误码与其"人话"解释、处理建议已在 `shared/src/errors.ts`（附录 D 唯一口径）定义好，前端此前只渲染了原始错误码。
相似度实际值已经能从任务详情接口的改写结果里拿到并挂在行上。删除能力此前完全不存在（没有清理入口）。

范围：明细页失败列表的一列渲染 + 一个操作按钮，以及配套的删除接口与清库逻辑。**不涉及**错误码口径变更、不涉及发布流程变更。

## Goals / Non-Goals

- Goals：失败原因可读（中文 + 阶段 + 实际值）；失败任务可清理且清得干净；已发布内容不可被删。
- Non-Goals：批量删除、撤销、改错误码定义、改相似度闸门值。

## 方案

### 失败原因渲染（前端派生）

`failureReason(errorCode, similarity)`：

- 无错误码 → 「—」；
- `SIMILARITY` → 带上实际相似度（`相似度 X 超过 0.45 闸门，已拦截`），闸门值取自 `SIMILARITY_THRESHOLD` 常量，不写死；
- 其它 → `阶段 + errorText(code)`（如「发布：无成功标志」），阶段前缀来自 `errorSpec(code).phase`，避免出现看不出是哪一步的短语。

单元格两行：中文原因（`.clamp` 截断，`title` 里带处理建议）+ 英文错误码小字（保留给排查用）。

### 删除（后端事务 + 状态闸门）

- `Pipeline.removeTask(id)`：任务不存在 → `NOT_FOUND`；状态 ≠ `failed` → `VALIDATION_FAILED`（提示"已发布的任务需要留证，不能删除"）；先 `publishQueue.remove(id)` 摘出队列，再 `taskRepo.deleteTask(id)`。
- `taskRepo.deleteTask(id)`：单事务按依赖顺序删 `fingerprint`（改写稿指纹）→ `publish_record` → `stock_image` → `task_log` → `rewrite_result` → `task`。
  **关键坑**：`task.rewrite_id` 反向引用 `rewrite_result`，必须先 `UPDATE task SET rewrite_id = NULL`，否则删改写稿会撞外键（首次实现就踩到，返回 `FOREIGN KEY constraint failed`）。
- 前端：仅 `failed` 行渲染删除按钮，点击后 `window.confirm` 二次确认，成功后 toast + 刷新汇总与列表。

## Alternatives Considered

| 方案                                               | 优点                                                                         | 缺点                                                             | 未选原因                                 |
| -------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------- |
| **A. 前端用 `shared/errors` 派生中文原因**（选中） | 不改接口契约；错误码口径本来就已在 `shared` 单点定义；能顺带用上已有的相似度 | 前端多一层映射逻辑                                               | —                                        |
| B. 后端在任务列表里带出 `errorMessage` 字段        | 前后端统一、前端无逻辑                                                       | 要改 `shared` 类型 + 列表接口 + 缓存；错误码口径多一处渲染出口   | 收益不抵改动面，且 A 已足够              |
| C. 删除改为「软删除」（加 `deleted_at`）           | 可恢复                                                                       | 列表/汇总/队列到处要加过滤条件，容易漏；失败任务本来就没留证价值 | 增加长期复杂度，与"删除即清库"的诉求不符 |

## 横切关注点

- **不可逆动作**：二次确认 + 仅 `failed` 可删 + 事务清库，删除后任务详情返回 404。
- **留证**：已发布任务禁止删除（与红线 7「发布幂等留证」同源），发布中任务禁止删除（避免队列指向空气）。
- **并发**：删除前先从发布队列摘除，避免队列里残留已删任务号。
- **可观测性**：删除写一条 `task N deleted by operator` 日志（带原错误码），并 `emitPipeline()` 推送前端刷新。
- **合规**：不涉及内容合规；删除只清本机数据。
