# 需求：单账号 → 多账号运营

## 背景

现状（v0.1.0）：

1. 账号身份写死在启动参数里 —— `process.env.ACCOUNT_NAME || 'toutiao-main'`，整个进程（`Pipeline` / `AccountService` / `CrawlService`）只为一个账号服务，想换账号必须改环境变量重启。
2. 发布队列是**进程级单例** `orchestrator/queue.ts` 的 `publishQueue`，所有任务进同一条队列。
3. 数据结构其实已经支持多账号：`account` 表 `name` 唯一、`task.account_id`、`source_item.account_id`、`data/sessions/<账号名>/` 独立浏览器目录（ADR-4）；缺的只是「多实例管理 + 界面切换」这一层。
4. 前端所有数据来自 `/api/summary` 的单个 `account` 字段，界面上没有「选哪个账号」的入口。

机会：多账号能带来「日额度按账号叠加」「一个账号掉登录 / 熔断不影响其他账号」「可按账号分题材运营」三个收益，且不触碰任何红线。

## 用户故事

- 作为**运营者**，我希望在一个控制台里添加多个头条账号并逐个扫码登录，以便不用反复改环境变量重启服务。
- 作为**运营者**，我希望在顶栏一键切换当前操作的账号，以便看板、素材池、任务列表、额度、熔断状态都跟着切换成这个账号的数据。
- 作为**运营者**，我希望每个账号各自计额度、各自按 ★15 分钟间隔串行发布、各自熔断，以便某个账号出问题时其他账号继续跑。
- 作为**风控负责人**，我不希望多账号导致「同一账号并行发布」或「多账号无节制并发」，以便不违反红线 9 与 ADR-5（风控优先于效率）。

## 验收标准（EARS 句式，必须可判定）

| ID          | 标准                                                                                                          | 判定方式                          |
| ----------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| REQ-0002-01 | WHEN 提交新账号名并确认 THEN 生成该账号记录与**独立**浏览器会话目录 `data/sessions/<账号名>/`，且返回列表包含它 | 接口测试 + 集成测试               |
| REQ-0002-02 | WHEN 把某账号切换为当前账号 THEN `/api/summary` 的 `account` / `quota` / `counts` / `circuit` 全部是该账号的数据 | 接口测试                          |
| REQ-0002-03 | WHEN 对账号 A 执行扫码登录 THEN 只读写 A 的会话目录，账号 B 的登录态保持原值                                   | 单元测试（路径）/ 集成测试（状态） |
| REQ-0002-04 | WHEN 同一账号有 ≥2 条任务在队列 THEN 严格串行发出，同一时刻该账号只有 1 条处于 `publishing`                     | 集成测试（并发断言）              |
| REQ-0002-05 | WHEN 多个账号同时有待发任务 THEN 同时发布的账号数 ≤ 「账号并发上限」设置值（默认 1）                           | 集成测试（调度器）                |
| REQ-0002-06 | WHEN 账号 A 当日额度耗尽或已熔断 THEN A 的新任务不放行，B 不受影响且可继续发布                                | 集成测试                          |
| REQ-0002-07 | WHEN 删除账号 THEN 若它是最后一个账号、或已有任务留证，则拒绝并给出原因；否则清记录并释放其浏览器上下文        | 接口测试                          |
| REQ-0002-08 | WHEN 老版本数据库（含 `toutiao-main`）升级 THEN 无需数据迁移，该账号自动成为默认当前账号并可正常使用           | 集成测试（旧库行为等价）          |
| REQ-0002-09 | WHEN 账号数 > 1 THEN 任务列表可看出每条任务属于哪个账号（列或筛选）                                           | 界面核对 / 自动化测试             |
| REQ-0002-10 | WHEN 任意账号执行发布 THEN 「取材网络」声明与「头条首发」断言照旧生效，不因多账号而产生绕过路径                | 既有测试不回归                    |

## Non-Goals（明确不做）

- **跨账号统一调度**：一次「一键开始」只作用于当前选中的账号；不做「给 A 分 3 条、给 B 分 5 条」的自动分配。
- **账号改名**：改名会牵连浏览器会话目录，先删后建更安全，本次不提供。
- **多用户 / 权限体系**：本机单人工具（§8.4），不做登录口令、角色。
- **代理隔离 / IP 轮换 / 指纹随机化**：超出本机工具范围，且属风控敏感手段，明确不碰。
- **会话目录自动清理**：删除账号只删库记录并释放上下文，`data/sessions/<账号名>/` 保留，避免误删登录态（涉及红线 6）。
- **跨账号素材共享变更**：去重仍是全局的（`allSimhashes()` + 指纹表），同一条原文不会被两个账号各发一遍 —— 这条维持现状，反而降低搬运判定风险。

## 影响面

- 涉及模块：
  - 编排层 `backend/src/orchestrator/`（队列从进程单例 → 按账号实例；新增账号运行时登记册与发布调度器）
  - 数据层 `backend/src/infra/db/repo/account.ts`（列表 / 当前账号 / 删除）、`repo/task.ts`、`repo/source-item.ts`（按账号过滤）
  - 接口层 `backend/src/api/`（新增账号资源路由；现有 summary / items / crawl / run / account-login 支持指定账号）
  - 契约层 `shared/src/types.ts`（`Summary` 带 `accounts` 与 `activeAccountId`；WS `account` 消息带账号 id）
  - 前端 `frontend/src/`（顶栏账号切换、设置页账号管理、明细页显示归属账号）
- 是否触碰红线：
  - 是 —— **红线 9「不许并行操作同一账号」**：方案用「每账号独立队列实例 + 账号锁」结构化保证，并加「账号并发上限」防止多账号一起变成事实上的并发洪峰（ADR-5 风控优先）。
  - 红线 4（脱敏）：新增日志字段为账号名 / 账号 id，无 cookie / token；`pino` redact 规则不变。
  - 其余红线未被触碰，既有断言（作品声明 / 头条首发 / 发布幂等）保持不回归。
