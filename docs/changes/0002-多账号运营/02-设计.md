# 设计：多账号运营

> 章节对齐 Google Design Doc：重点是**权衡**，不是实现手册。

## Context and Scope

**已有事实**（读代码所得，不要凭记忆）：

- `account` 表：`name` 唯一、`user_data_dir`、`status`、`daily_publish_limit`、`used_today`、`quota_date`、`circuit`、`last_publish_at` —— **已经是「每账号一份」的额度与熔断器**。
- `task.account_id` / `source_item.account_id` —— 数据天然按账号归属。
- `infra/playwright/session.ts`：`toutiaoContext(name)` → `getPersistentContext('toutiao:' + name, accountSessionDir(name))`，按 key 缓存并空闲释放 —— **会话隔离已在位（ADR-4）**。
- `orchestrator/queue.ts`：`export const publishQueue = new PublishQueue()` —— **唯一的进程级单例**，也是「只能跑一个账号」的真正根因。
- `createDefaultDeps()`：`const name = process.env.ACCOUNT_NAME || DEFAULT_ACCOUNT_NAME` 一次性构造 `Pipeline` / `AccountService` / `CrawlService` —— 账号身份在启动时固化。

**范围**：把「一个进程 = 一个账号」改造成「一个进程 = N 个账号实例 + 一个当前选中项」，其中 N ≥ 1 且默认行为与今天完全一致。

**不在范围**：跨账号统一调度（01-需求.md 的 Non-Goals）、代理 / IP 隔离、账号改名。

## Goals / Non-Goals

Goals：

1. 账号可增删列表、可扫码登录、可切换，且切换后界面看到的全是该账号的数据。
2. 每个账号有自己的发布队列、额度、最小间隔、熔断器 —— 互不影响。
3. 结构上保证「同一账号严格串行」（红线 9），并对「多账号同时发布」设一个显式上限。
4. 老库零迁移升级，`toutiao-main` 自动成为默认账号。

Non-Goals（本来可以是目标、但明确放弃）：

- 让多账号真正「并行提吞吐」：默认并发上限为 1，多账号的价值是**隔离**（额度、登录态、故障域），不是提速。
- 给每个账号配不同的提示词 / 图库 / 黑名单：配置仍是全局（`app_config`），本次不做账号级配置。
- 自动把所有账号的登录都刷一遍：单人本机工具，登录动作必须人自己做（§3.5）。

## 方案

### 概览

```
                  ┌───────────── 前端：顶栏「当前账号」下拉 + 设置页「账号列表」 ─────────────┐
                  │        GET /api/summary?accountId=   POST /api/accounts/:id/activate     │
                  └───────────────────────────────┬─────────────────────────────────────────┘
                                                  │
backend  api/routes/*  ──►  AccountRuntime（登记册）  ──►  per-account: Pipeline | CrawlService | AccountService
                                  │                                    │
                                  │ 当前账号落在 app_config.activeAccountId（ADR-10）        │
                                  │                                    ▼
                                  │                    每账号一个 PublishQueue 实例（不再是单例）
                                  ▼
                     PublishScheduler：全局「同时在发布的账号数 ≤ maxConcurrentAccounts」
```

三层职责：

| 层                      | 新增/改造                                                       | 职责                                                     |
| ----------------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| `AccountRuntime`（新增） | `orchestrator/registry.ts`                                       | 账号清单、当前账号、按账号惰性构造 Pipeline/Crawl/登录服务、统一启停 |
| `PublishScheduler`（新增） | `orchestrator/publishScheduler.ts`                               | 跨账号的发布并发闸门 + FIFO 等待唤醒                      |
| `Pipeline`（改造）        | 持有自己的 `PublishQueue`；所有查询按 `account_id` 过滤           | 保持原有单账号语义，只是不再共享全局状态                  |

### 细节 1：账号身份怎么传

- **当前账号持久化在 `app_config.activeAccountId`**（ADR-10：可调项进 `app_config`）。理由：本机单人工具，界面刷新 / 服务重启后应停在同一个账号上；也避免引入新的表和迁移。
- 读取顺序：`activeAccountId` → 该 id 存在则用 → 否则回落到 `account` 表首个账号 → 再否则 `ensureAccount(DEFAULT_ACCOUNT_NAME)`。**这条回落保证老库零迁移**（REQ-0002-08）。
- 接口入参：需要指定账号的地方统一支持**可选** `accountId`（body 或 query），不传就用当前账号。理由：让 `/api/run`、`/api/crawl` 这类已存在的接口保持向后兼容，已有测试与调用方式不用改。

### 细节 2：队列从单例到按账号实例

`PublishQueue` 的语义（FIFO、`tryLock` 串行、`position`/`eta`）完全不动，只是不再导出单例：

- `Pipeline` 增加实例字段 `readonly queue = new PublishQueue()`，内部所有 `publishQueue.*` 改为 `this.queue.*`；
- `queueInfo()` / `drainQueue()` 仍按interval给 ETA，语义不变；
- `risk.test.ts` 里直接 import 单例的那两个用例改为 `new PublishQueue()` —— 类的行为没变，只是去掉了共享可变状态。

**为什么不动类本身**：LRU/ETA/锁这套逻辑是被生产事故打磨过的（2026-10-22 并发误判），复用它比重写一个「多账号队列」安全得多。

### 细节 3：跨账号并发闸门

```ts
scheduler.acquire(accountId, retry)  // 已在发布中的账号允许重入；否则看当前活跃数是否 < 上限
scheduler.release(accountId)         // 让出名额，并按 FIFO 唤醒下一个等待的账号
```

- 上限取自可调项 `accountConcurrencyLimit`（默认 `1`，范围 1–5），进 `APP_CONFIG_DEFS` —— 走 ADR-10 的既定通路，界面与后端双重校验。
- **默认 1 = 与今天完全等价**：多账号默认仍是「全进程一次只发一条」，把「同时给多个账号开浏览器」变成需要人显式放开的选项，符合 ADR-5（风控优先于效率）。
- FIFO 唤醒而不是让各账号 tick 自己重试：避免「手快先占、后面的饿死」，也让等待时长可预期。
- 账号自己的队列锁（`queue.tryLock()`）与调度器是两把不同的锁：前者保证**同账号串行**（红线 9），后者限制**跨账号并发**（ADR-5）。

### 细节 4：数据与参数的归属

| 数据               | 归属粒度   | 说明                                                       |
| ------------------ | ---------- | ---------------------------------------------------------- |
| 额度 / used_today  | 每账号      | 已在表里，天然隔离                                         |
| 最小发布间隔       | 每账号      | `account.last_publish_at`，天然隔离                         |
| 熔断 / 连续失败    | 每账号      | 已在表里；「不许自动恢复」语义不变（红线 8）                 |
| 浏览器会话         | 每账号目录  | ADR-4 已在位；切换账号要 `releaseContext` 让出资源           |
| 素材池 / 任务      | 每账号      | `listUntasked(accountId)`、`listTasks(status, limit, accountId)` |
| 内容去重指纹       | **全局**    | 维持现状：同一原文不会被两个账号各发一遍（降搬运风险）       |
| 提示词 / 图库 / 黑名单 / 额度上限 | 全局 | 本次不做账号级配置（Non-Goal）                |

### 细节 5：接口清单

| 方法    | 路径                              | 说明                                            |
| ------- | --------------------------------- | ----------------------------------------------- |
| GET     | `/api/accounts`                   | 账号列表（含队列深度 / 待复核 / 失败数）         |
| POST    | `/api/accounts`                   | `{ name }` 新建账号（重名 → 400 `ACCOUNT_EXISTS`） |
| POST    | `/api/accounts/:id/activate`      | 切换当前账号                                     |
| DELETE  | `/api/accounts/:id`               | 删除账号（最后一个 / 有留证 → 400）              |
| GET     | `/api/summary`                    | 返回当前账号 + `accounts[]` + `activeAccountId`  |
| POST    | `/api/account/login/start` 等      | 支持 `accountId`，默认当前账号                   |
| POST    | `/api/run` `/api/crawl`           | 支持 `accountId`，默认当前账号                   |
| GET     | `/api/tasks` `/api/items`         | 支持 `accountId`（默认当前账号）                  |

契约变化集中在 `Summary`：`accounts: AccountOverview[]` + `activeAccountId: number`；WS `account` 消息 payload 增加 `id`，让前端知道这次推送属于哪个账号。

### 细节 6：删除账号的边界

- 拒绝删除**最后一个账号**（删了系统没法用）；
- 拒绝删除**已有任务**的账号（`task` 有该 `account_id` 的行）—— 已发布的内容必须留证（§2.3 验收口径 6），不提供「连任务一起删」的级联删除；
- 通过时：释放该账号的浏览器上下文 → 删 `account` 行（此时必无任务，外键无引用）；
- `data/sessions/<账号名>/` **保留**，并在返回里给出路径由人自行处置 —— 删错账号不至于把登录态一起带走。

## Alternatives Considered

| 方案                                                       | 优点                                     | 缺点                                                            | 未选原因                                                   |
| ---------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
| A. 维持单账号，用 `ACCOUNT_NAME` 起多个进程 + 多个端口      | 改动最小，进程天然隔离                     | 要起 N 个后端 + N 个前端，data/ 冲突、配额分散、体验割裂          | 与「一个控制台运营多个账号」的目标背道而驰                  |
| B. 全部并行：每账号一条队列，无跨账号闸门                    | 吞吐最高                                  | 一次开 N 个浏览器同 IP 群发，直接违背 ADR-5 风控优先             | 红线相关，明确不做                                          |
| **C. 每账号队列 + 全局并发闸门（默认 1）**                   | 结构保证同账号串行；多账号默认是隔离而非提速；想提速要显式放开 | 多了一层调度器；默认吞吐没提升                                  | **选它**：收益是隔离，风险可控且可调                        |
| D. 给 `account` 表加 `is_active` 列（迁移落库）              | 当前账号是真列，查询直观                   | 需要新迁移（不可逆），且要额外维护「唯一 active」约束            | 与 ADR-10「可调项进 app_config」冲突，且没必要引入迁移      |

## 横切关注点

- **风控与限速**：同账号串行（队列实例 + 账号锁）不变；跨账号并发默认 1，可调但上限 5；浏览器上下文空闲释放规则不变（★5 分钟）。多个持有 diverge session 的浏览器同时开着会占内存，因此**切换当前账号时释放前一个账号的上下文**。
- **幂等与不可逆动作**：发布幂等（红线 7）逻辑一行不动；删除账号是本次唯一的不可逆动作 → 三重闸门（末位保护 / 留证保护 / 会话不删）。
- **合规（声明 / 首发）**：`FORCE_DECLARATION` 与 `assertFirstPublishUnchecked` 在 `PublishService` 里，与账号无关；新增的并发路径同样经过它，不存在绕过。
- **数据脱敏与敏感信息**：新增日志字段只有 `accountId` / `account` 名；二维码依旧只走 WS 推送不落盘（§8.4）；`pino` redact 规则不变。`storageStatePath` 已在 redact 列表里，界面展示保持现有写法（本机工具，已在 README 声明）。
- **可观测性**：日志统一带 `account` 字段便于按账号过滤；WS `account` / `pipeline` 消息带 `accountId`，前端据此刷新；告警文案带账号名，避免「不知道是哪个账号熔断了」。
- **性能**：多个账号意味着多个 tick（15 秒一轮）与多个 `countByStatus`；查询一律按 `account_id` 过滤，不给全表扫描留口子。
